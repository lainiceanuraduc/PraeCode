class="clean-btn tocCollapsibleButton_TO0P">On this page</button></div><div class="theme-doc-markdown markdown"><header><h1>ACP Host Integration</h1></header>
<p>Python dependency commands on this page use a
<a class="" href="/docs/reference/package-management#developer-workflow">PM-prepared source checkout</a>.
After a dependency change, reactivate the checkout and restart Hermes.</p>
<p>Hermes Agent can run as an ACP server, letting ACP-compatible hosts talk to
Hermes over stdio. Editors can render:</p>
<ul>
<li class="">chat messages</li>
<li class="">tool activity</li>
<li class="">file diffs</li>
<li class="">terminal commands</li>
<li class="">approval prompts</li>
<li class="">streamed thinking / response chunks</li>
</ul>
<p>Other hosts can use the same protocol to route collaboration events into
Hermes. ACP is a good fit when you want Hermes to keep its existing identity,
provider setup, memory, skills, and tools while another application owns the
conversation transport.</p>
<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="what-hermes-exposes-in-acp-mode">What Hermes exposes in ACP mode<a href="#what-hermes-exposes-in-acp-mode" class="hash-link" aria-label="Direct link to What Hermes exposes in ACP mode" title="Direct link to What Hermes exposes in ACP mode" translate="no">​</a></h2>
<p>Hermes runs with a curated <code>hermes-acp</code> toolset designed for editor workflows. It includes:</p>
<ul>
<li class="">file tools: <code>read_file</code>, <code>write_file</code>, <code>patch</code>, <code>search_files</code></li>
<li class="">terminal tools: <code>terminal</code>, <code>process</code></li>
<li class="">web/browser tools</li>
<li class="">memory, todo, session search</li>
<li class="">skills</li>
<li class="">execute_code and delegate_task</li>
<li class="">vision</li>
</ul>
<p>It intentionally excludes things that do not fit typical editor UX, such as messaging delivery and cronjob management.</p>
<p>The toolset resolves the same way as on the messaging gateway for the same
platform config. That includes the extras the gateway adds on top of the
list, such as enabled plugin toolsets, so ACP sessions get those too.
<code>platform_toolsets.acp</code> replaces the <code>hermes-acp</code> default, and
<code>agent.disabled_toolsets</code> removes toolsets from every ACP session. MCP
servers from <code>mcp_servers</code> follow the same rules too. By default ACP gets
every enabled server. If you list server names in <code>platform_toolsets.acp</code>,
only those servers are included, and <code>no_mcp</code> drops them all. <code>hermes tools</code>
has no ACP entry, so edit <code>config.yaml</code> directly:</p>

<p>MCP servers that the editor sends with <code>session/new</code> are separate. The
client asks for them per session, and they are always added.</p>
<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="editor-provided-mcp-servers">Editor-provided MCP servers<a href="#editor-provided-mcp-servers" class="hash-link" aria-label="Direct link to Editor-provided MCP servers" title="Direct link to Editor-provided MCP servers" translate="no">​</a></h2>
<p>On gateways advertising <code>acp-session-mcp-v1</code>, editor <code>mcpServers</code> belong to the
canonical session, not the ACP viewer process. The gateway uses separate registry
namespaces even when two editors supply the same server name. Closing an editor
does not cancel another session&#x27;s MCP execution.</p>
<p>Discovery is eager and bounded before the first model turn. The selected tool
schemas remain frozen for the conversation; server tool-list changes require a
new session. MCP transports are released after each execution, without stopping
sibling sessions or the shared MCP loop.</p>
<p>The gateway keeps the editor transport specification (including command arguments,
environment values and HTTP headers) only in memory. Durable session policy holds
a fingerprint and the selected schemas, not a copy of those credentials. After a
gateway restart, the editor must supply the same <code>mcpServers</code> on load/resume.
Missing credentials refuse execution; a changed specification or secret refuses
reattachment rather than silently changing the session. Start a new session when
changing the server configuration. Commands and paths run on the gateway host.</p>

<h3 class="anchor anchorTargetStickyNavbar_Vzrq" id="buzz-channels-relay-bridge">Buzz channels (relay bridge)<a href="#buzz-channels-relay-bridge" class="hash-link" aria-label="Direct link to Buzz channels (relay bridge)" title="Direct link to Buzz channels (relay bridge)" translate="no">​</a></h3>
<p><a href="https://github.com/block/buzz" target="_blank" rel="noopener noreferrer" class="">Buzz</a> is a Nostr-based collaboration platform
for people and agents. Its <code>buzz-acp</code> harness connects Buzz channels to any ACP
agent over stdio:</p>
<div class="language-text codeBlockContainer_Ckt0 theme-code-block" style="--prism-color:#F8F8F2;--prism-background-color:#282A36"><div class="codeBlockContent_QJqH"><pre tabindex="0" class="prism-code language-text codeBlock_bY9V thin-scrollbar" style="color:#F8F8F2;background-color:#282A36"><code class="codeBlockLines_e6Vv"><div class="token-line" style="color:#F8F8F2"><span class="token plain">Buzz relay &lt;-- WebSocket --&gt; buzz-acp &lt;-- ACP over stdio --&gt; Hermes Agent</span><br></div></code></pre></div></div>

<p>(This is distinct from <a href="#buzz-desktop" class="">Buzz Desktop&#x27;s managed runtime</a>, which

<li class="">Configure Hermes provider credentials first with <code>hermes model</code>, or set them in <code>~/.hermes/.env</code> / <code>~/.hermes/config.yaml</code>.</li>
</ul>
<h3 class="anchor anchorTargetStickyNavbar_Vzrq" id="jetbrains">JetBrains<a href="#jetbrains" class="hash-link" aria-label="Direct link to JetBrains" title="Direct link to JetBrains" translate="no">​</a></h3>
<p>Use an ACP-compatible plugin and point it at <code>hermes acp</code> or <code>hermes-acp</code>.</p>
<h3 class="anchor anchorTargetStickyNavbar_Vzrq" id="buzz-desktop">Buzz Desktop<a href="#buzz-desktop" class="hash-link" aria-label="Direct link to Buzz Desktop" title="Direct link to Buzz Desktop" translate="no">​</a></h3>
<p><a href="https://github.com/block/buzz" target="_blank" rel="noopener noreferrer" class="">Buzz</a> ships Hermes Agent as a preset runtime.
With Hermes installed the normal way, Buzz discovers it automatically —
open <strong>Settings → Runtimes</strong> and Hermes appears under your runtimes.</p>
<p>If discovery fails (older installs), make sure the ACP launcher resolves on a
login-shell PATH:</p>
<div class="language-bash codeBlockContainer_Ckt0 theme-code-block" style="--prism-color:#F8F8F2;--prism-background-color:#282A36"><div class="codeBlockContent_QJqH"><pre tabindex="0" class="prism-code language-bash codeBlock_bY9V thin-scrollbar" style="color:#F8F8F2;background-color:#282A36"><code class="codeBlockLines_e6Vv"><div class="token-line" style="color:#F8F8F2"><span class="token builtin class-name" style="color:rgb(189, 147, 249)">command</span><span class="token plain"> </span><span class="token parameter variable" style="color:rgb(189, 147, 249);font-style:italic">-v</span><span class="token plain"> hermes-acp </span><span class="token operator">||</span><span class="token plain"> </span><span class="token builtin class-name" style="color:rgb(189, 147, 249)">command</span><span class="token plain"> </span><span class="token parameter variable" style="color:rgb(189, 147, 249);font-style:italic">-v</span><span class="token plain"> hermes</span><br></div></code></pre></div></div>
<p>Recent installs write both <code>hermes</code> and <code>hermes-acp</code> launchers into
<code>~/.local/bin</code>; running <code>hermes update</code> adds the <code>hermes-acp</code> launcher to
older installs. As a manual fallback, configure Buzz&#x27;s agent command as
<code>hermes</code> with args <code>[&quot;acp&quot;]</code>.</p>
<h4 class="anchor anchorTargetStickyNavbar_Vzrq" id="model-picker">Model picker<a href="#model-picker" class="hash-link" aria-label="Direct link to Model picker" title="Direct link to Model picker" translate="no">​</a></h4>
<p>Buzz Desktop (v0.5.1+) renders Hermes&#x27; full model menu in the agent&#x27;s runtime
settings. The list comes from Hermes itself over ACP: it shows every model
from providers you have authenticated in Hermes (the same inventory behind
<code>hermes model</code> and the <code>/model</code> command), so a model missing from the menu
means its provider has no credentials configured on the Hermes side.</p>
<p>Entry IDs take the form <code>provider:model</code> (e.g. <code>openrouter:z-ai/glm-5.1</code>), or
<code>custom:&lt;name&gt;:&lt;model&gt;</code> for custom OpenAI-compatible endpoints defined in
<code>config.yaml</code>. Picking a model applies to that agent&#x27;s session; it does not
change your Hermes-wide default — use <code>hermes model</code> for that.</p>
<h4 class="anchor anchorTargetStickyNavbar_Vzrq" id="keep-buzz-agents-owner-only">Keep Buzz agents owner-only<a href="#keep-buzz-agents-owner-only" class="hash-link" aria-label="Direct link to Keep Buzz agents owner-only" title="Direct link to Keep Buzz agents owner-only" translate="no">​</a></h4>
<p>Buzz creates every agent with <strong>Who can talk to this agent</strong> set to <code>Owner only</code>.
Leave it there when the runtime is Hermes.</p>
<p>Two behaviors combine on this path. The <code>hermes-acp</code> toolset includes <code>terminal</code>
and <code>execute_code</code>, and Buzz&#x27;s ACP bridge answers Hermes&#x27; permission requests
itself with <code>allow_once</code> rather than surfacing them. A Hermes agent in Buzz
therefore runs shell commands on the host without prompting. I asked one to run
<code>rm -rf</code> against a scratch directory and it deleted it, no prompt anywhere.</p>
<p>Selecting <code>Anyone</code> hands that same shell access to every author who can reach
the channel. Buzz does not warn when you pick it.</p>
<p><code>approvals.mode: manual</code> does not help: Hermes raises the permission request,
but Buzz auto-approves it and the command still runs. To take the shell away,
narrow the toolset instead: set <code>platform_toolsets.acp</code> to a list without
<code>terminal</code> and <code>code_execution</code>, or add them to <code>agent.disabled_toolsets</code>.
Even an empty <code>platform_toolsets.acp: []</code> still adds enabled plugin
toolsets, so name any plugin toolset you want gone in
<code>agent.disabled_toolsets</code>.</p>
<p><code>!shutdown</code> from the owner stops the agent in any mode, and Buzz ignores that
command from everyone else.</p>
<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="configuration-and-credentials">Configuration and credentials<a href="#configuration-and-credentials" class="hash-link" aria-label="Direct link to Configuration and credentials" title="Direct link to Configuration and credentials" translate="no">​</a></h2>
<p>ACP mode uses the same Hermes configuration as the CLI:</p>
<ul>
<li class=""><code>~/.hermes/.env</code></li>
<li class=""><code>~/.hermes/config.yaml</code></li>
<li class=""><code>~/.hermes/skills/</code></li>
<li class=""><code>~/.hermes/state.db</code></li>
</ul>
<p>Provider resolution uses Hermes&#x27; normal runtime resolver, so ACP inherits the currently configured provider and credentials. Hermes also advertises a terminal auth method (<code>--setup</code>) for first-run ACP clients; this opens Hermes&#x27; interactive model/provider setup.</p>
<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="host-integration">Host integration<a href="#host-integration" class="hash-link" aria-label="Direct link to Host integration" title="Direct link to Host integration" translate="no">​</a></h2>
<p>Older ACP hosts may still set this variable on the Hermes subprocess they
spawn. It is not user configuration — do not set it by hand in <code>.env</code> or
<code>config.yaml</code>.</p>
<table><thead><tr><th>Variable</th><th>Value</th><th>Effect</th></tr></thead><tbody><tr><td><code>HERMES_ACP_SKIP_CONFIGURED_MCP</code></td><td><code>1</code></td><td><strong>No effect.</strong> Hermes no longer reads it. <code>hermes acp</code> / <code>hermes-acp</code> runs as a viewer of the gateway daemon and never starts the <code>config.yaml</code> MCP servers itself, so there is no ACP-side startup to skip.</td></tr></tbody></table>
<p>The ACP process does no MCP discovery. The gateway daemon starts the
<code>mcp_servers</code> from its own profile&#x27;s <code>config.yaml</code> once at gateway boot, and ACP
sessions get those servers through the <code>platform_toolsets.acp</code> rules
<a href="#what-hermes-exposes-in-acp-mode" class="">above</a>. Setting the variable on the ACP
subprocess or on the gateway does not change that. Use <code>platform_toolsets.acp</code>
or <code>no_mcp</code> to keep configured servers out of ACP sessions.</p>
<p>The editor&#x27;s <code>session/new</code> <code>mcpServers</code> are passed to the gateway and attached
to that canonical session (see
<a href="#editor-provided-mcp-servers" class="">Editor-provided MCP servers</a>), whether or not
the variable is set.</p>
<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="session-behavior">Session behavior<a href="#session-behavior" class="hash-link" aria-label="Direct link to Session behavior" title="Direct link to Session behavior" translate="no">​</a></h2>
<p>ACP sessions are tracked by the ACP adapter&#x27;s in-memory session manager while the server is running.</p>
<p>Each session stores:</p>
<ul>
<li class="">session ID</li>
<li class="">working directory</li>
<li class="">selected model</li>
<li class="">current conversation history</li>
<li class="">cancel event</li>
</ul>
<p>Conversations are persisted to Hermes&#x27; session database and can be listed, loaded,
resumed, or forked after the ACP server restarts. Opening a new session without a
prompt keeps it in memory only: model-discovery probes do not create empty history
rows. A nonempty fork is persisted immediately, and existing session metadata can
still be updated even when its current history is empty.</p>
<p>Existing empty rows from older versions are not automatically deleted. An open ACP
row does not prove its client has disconnected. After closing the relevant editor
sessions, inspect unwanted rows with <code>hermes sessions show &lt;id&gt;</code> and remove only
confirmed unwanted sessions with <code>hermes sessions delete &lt;id&gt;</code>.</p>
<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="working-directory-behavior">Working directory behavior<a href="#working-directory-behavior" class="hash-link" aria-label="Direct link to Working directory behavior" title="Direct link to Working directory behavior" translate="no">​</a></h2>
<p>ACP sessions bind the editor&#x27;s cwd to the Hermes task ID so file and terminal tools run relative to the editor workspace, not the server process cwd.</p>
<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="approvals">Approvals<a href="#approvals" class="hash-link" aria-label="Direct link to Approvals" title="Direct link to Approvals" translate="no">​</a></h2>
<p>Dangerous terminal commands can be routed back to the editor as approval prompts. ACP approval options are simpler than the CLI flow:</p>
<ul>
<li class="">allow once</li>
<li class="">allow always</li>
<li class="">deny</li>
</ul>
<p>Whether you actually see a prompt is up to the host. A host is free to answer the
request programmatically instead of showing it to you, in which case these
options exist on the wire but never reach a human. Buzz Desktop does this, so
treat that path as unattended execution regardless of your <code>approvals</code> setting.</p>
<p>On timeout or error, the approval bridge denies the request. The wait is
<code>approvals.timeout</code> from <code>config.yaml</code> (default 300 s), the same knob the CLI and
gateway prompts use — raise it if your editor keeps approval cards open longer.</p>
<h3 class="anchor anchorTargetStickyNavbar_Vzrq" id="session-scoped-edit-auto-approval">Session-scoped edit auto-approval<a href="#session-scoped-edit-auto-approval" class="hash-link" aria-label="Direct link to Session-scoped edit auto-approval" title="Direct link to Session-scoped edit auto-approval" translate="no">​</a></h3>
<p>ACP exposes a third tier between <em>allow once</em> and <em>allow always</em>: <strong>Allow for session</strong>. Picking it from the editor&#x27;s permission prompt records the approval inside the current ACP session only — every subsequent matching command in that session goes through without prompting, but a new ACP session (or restarting the editor) resets the slate and re-prompts the first time.</p>
<table><thead><tr><th>Option</th><th>Editor label</th><th>Scope</th><th>Persisted across restarts</th></tr></thead><tbody><tr><td><code>allow_once</code></td><td>Allow once</td><td>This one tool call</td><td>No</td></tr><tr><td><code>allow_session</code></td><td>Allow for session</td><td>All matching calls in this ACP session</td><td>No — cleared when the session ends</td></tr><tr><td><code>allow_always</code></td><td>Allow always</td><td>All future sessions</td><td>Yes (written to the Hermes permanent allowlist)</td></tr><tr><td><code>deny</code></td><td>Deny</td><td>This one tool call</td><td>No</td></tr></tbody></table>
<p><code>allow_session</code> is the right default for an editor workflow where you trust an agent for the duration of a task but don&#x27;t want to grant a long-lived allowlist entry. The safety trade-off is straightforward: the broader the scope, the less the editor will interrupt you, and the more damage a misbehaving agent (or prompt injection) can do before you notice. Start with <code>allow_once</code> for unfamiliar commands; promote to <code>allow_session</code> once you&#x27;ve seen the agent run the same pattern correctly a few times; reserve <code>allow_always</code> for truly idempotent commands you trust forever (e.g. <code>git status</code>).</p>
<p>The ACP bridge maps these options onto Hermes&#x27; internal approval semantics — <code>allow_always</code> writes a permanent allowlist entry the same way the CLI does, while <code>allow_session</code> only affects the in-process approval cache for the current ACP session.</p>
